# Консолидация/синтез из источников → provenance + verify-гейт (anti-галлюцинация, HARD)

> **Установлено:** 2026-06-14 (Антон, сессия OPS, консолидация 6 файлов процессов). Запрос: «нужно ли фл добавить во избежание очередных галлюцинаций» при сведении нескольких файлов в один.
> **Корень:** когда агент СВОДИТ несколько источников (файлы/таблицы/доки) в один документ, он может ДОБАВИТЬ блок, которого нет ни в одном источнике (правдоподобная выдумка). Пометки `[из rules]`/`[TODO]` снижают риск, но без сверки «каждый блок прослеживается к источнику» галлюцинация проходит.
> **Связано:** `factcheck.md`/`quality.md` (фактчек перед готово), `determinism-first-and-verify.md` (verify-гейт), `bulletproof-patterns.md` (#5 verified-only), `no-smoothing.md`, `no-false-negative.md`, `numbers-deterministic-meaning-llm.md`, `model-bakeoff.md` (PROVENANCE).

## Правило (применять при ЛЮБОМ синтезе из 2+ источников)
Документ, собранный/сведённый из нескольких источников (консолидация файлов, сводка отчётов, merge таблиц, «собери из X,Y,Z один»), ОБЯЗАН:

### 1. PROVENANCE на каждый содержательный блок
Каждый раздел/факт/число/процесс помечен происхождением:
- `[из: <файл/лист/источник>]` — взято из конкретного источника.
- `[дополнено из rules: <правило>]` — добавлено из наших правил/SOP (НЕ из исходников) — и это правило реально содержит утверждение.
- `[TODO: уточнить]` — честный пробел, не выдумывать.
Блок без одной из трёх пометок = подозрение на галлюцинацию.

### 2. VERIFY-ГЕЙТ перед «готово» (обязателен)
Перед тем как считать консолидацию готовой / коммитить / показать — прогнать **strict-factcheck против источников** (агент `strict-factchecker` ИЛИ скрипт): каждый блок → ✅ TRACEABLE / 📘 FROM-RULES (правило проверено) / 🟡 TODO / 🔴 HALLUCINATION / ⚠️ DISTORTED (число/факт искажён).
**Вердикт:** PASS (0 🔴) / REVIEW (⚠️) / FAILED (🔴). FAILED/REVIEW → исправить помеченное → перепроверить → только потом готово.

### 3. Числа — дословно из источника (numbers-deterministic-meaning-llm)
Числа/коды/цены/проценты/имена в консолидации — сверять дословно с источником. «Прошло через LLM-сведение» = UNCONFIRMED пока не сверено.

### 0. СКАНИРОВАНИЕ источников = ДЕТЕРМИНИРОВАННЫМ кодом, не «на глаз» LLM (Антон 2026-06-14)
> «Чтобы не было ошибок в оценке И вообще ошибок в сканировании документов» — через **Workflow**.

Перед консолидацией источники сканируются **детерминированным extractor'ом** (Python: openpyxl читает ВСЕ листы; python-docx — ВСЕ абзацы/таблицы; pdf — pdftotext), который выгружает ПОЛНЫЙ сырой дамп (ничего не пропуская: все sheets, все строки, все абзацы). LLM **НЕ сканирует сам** (может пропустить лист / неверно распарсить — «ошибка сканирования») — LLM консолидирует СМЫСЛ из готового полного дампа. Числа/коды/таблицы переносятся из дампа дословно (numbers-deterministic-meaning-llm).
- **Полнота сканирования = проверяемо:** extractor печатает инвентарь (N листов × M строк, N абзацев) → сверить что всё отражено в консолидации (ни один лист не потерян).
- **Реализация = Workflow** (детерминированный скелет): `extract (код) → merge (LLM по дампу) → verify-гейт (strict против дампа)`. Не разовый агент «прочитай и сведи» (тот может пропустить/выдумать — ошибка и сканирования, и оценки).

## Когда применять / не применять
- **Применять:** консолидация файлов, сводные отчёты, merge данных, «собери из нескольких в один», дайджесты из источников, синтез research.
- **Не применять:** оригинальный черновик с нуля (нет источников для сверки — там обычный factcheck чисел); тривиальная склейка 2 строк.

## Антипаттерны
- ❌ Консолидация «готова» без verify-гейта против источников (галлюцинация-блок проходит).
- ❌ Блок без provenance-пометки выдан как факт.
- ❌ Число из сведения не сверено дословно с источником.
- ❌ Дополнение «из rules» с несуществующим/не содержащим правилом.
