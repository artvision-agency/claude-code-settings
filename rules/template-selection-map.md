# Карта выбора шаблона — как Антону задавать класс артефакта, чтобы визуал был стабильно сильным

> **Установлено:** 2026-06-08 (Антон: «иногда делаешь очень классные, иногда очень слабые HTML с графиками — нужна карта как выбрать определённый шаблон среди наших сделанных для анализа/аудита/etc»).
> **Корень проблемы:** визуал слабый, когда я собираю структуру/дизайн «из головы» вместо открытия готового канон-шаблона (self-corrections #23/#24, seo-presale-audit-workflow, analyzed-project-design-system). Сильный — когда беру эталон + дизайн-систему клиента.
> **Связано:** `kp-workflow-family.md` (роутер КП), `seo-presale-audit-workflow.md`, `analyzed-project-design-system.md`, `design-profile-routing.md`, `document-list-format.md`, `mobile-first-all-html.md`, `_compliance-checklist.md`, `internal-docs-plain-tables.md`, `always-html-deploy-links.md`, `prompt-elaboration.md`.

## Главный принцип (почему бывает слабо)
**Сильный визуал = эталон-шаблон + дизайн-система клиента + графики из данных.** Слабый = «придумал структуру и тему сам». Поэтому: ПЕРЕД сборкой любого визуального артефакта Claude ОБЯЗАН (а) определить КЛАСС, (б) открыть его эталон-spec, (в) извлечь дизайн-систему клиента с его сайта. Если Антон хочет конкретный шаблон — называет ярлык из таблицы ниже.

## Как Антон выбирает шаблон (3 способа)
1. **Ярлык класса** — короткое слово из колонки «Ярлык» (напр. «сделай как seo-presale», «формат visibility», «как USmile-гант», «внутренняя ч/б таблица»). Я беру именно тот эталон.
2. **«Как у <клиент/проект>»** — указать готовый артефакт-референс («как дашборд USmile», «как КП Doctra»). Я открываю тот файл и повторяю структуру+качество в дизайне нового клиента.
3. **Ничего не указал** — я сам определяю класс по задаче (таблица ниже) и называю в строке `[РАЗВЁРТКА: … паттерн: <класс+эталон>]` ДО сборки. Антон видит выбор и может поправить одним словом.

## Универсальные правила качества визуала (для ВСЕХ клиентских HTML)
Применяю всегда, независимо от класса (это и есть разница «классно vs слабо»):
1. **Дизайн-система клиента, не дефолт** — `curl <сайт> + styles.css | grep '#hex' + font-family` → применить (`analyzed-project-design-system.md`). НЕ дефолтная тёмная.
2. **Графики = CSS-бары из данных** (width:% = value/max), пропорции точные ≤3% (`kp-workflow-family` §2). НЕ скриншоты-простыни; скрин = доказательство в попап-lightbox.
3. **Структуры — списками** (`document-list-format.md`); числа — с источником+датой (`calculations-need-sources.md`); прогноз «оценочно».
4. **Mobile-first** (min-width), автономный HTML (без CDN), TOC сверху, бренд Artvision (прямой клиент) / без (AdvertMed).
5. **Фото HIGH-res** (`image-quality-standard.md`), без растяжения (cover не fill).
6. **Пост-деплой самопроверка скриншотом 1440+375 глазами** (`post-deploy-selfcheck.md`) + deploy-URL первой строкой.
7. Сверка с `_compliance-checklist.md` перед «готово».

## Что делать Антону, если визуал вышел слабым
Сказать: **«слабый визуал, пересобери по эталону <ярлык>»** ИЛИ **«возьми дизайн как у <клиент>»**. Я: открою эталон-spec + извлеку дизайн-систему клиента + пересоберу. Не «подкрашу» старое, а пересоберу по канону.

## Антипаттерны (ровно причины «слабых» версий)
- ❌ Собирать структуру/тему «из головы» вместо открытия эталон-spec (self-corrections #24).
- ❌ Дефолтная тёмная тема вместо дизайн-системы клиента (#23, analyzed-project-design-system).
- ❌ Гигантские скриншоты-простыни вместо нативных CSS-графиков (Doctra-прецедент).
- ❌ Скрин/таблица в чате вместо HTML deploy-URL (always-html-deploy-links).
- ❌ Внутренний аудит в клиентском бренд-дизайне (internal-docs-plain-tables) или клиентский — в ч/б.
- ❌ «Готово» без самопроверки скриншотом глазами.
