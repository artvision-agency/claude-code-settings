## ОСЬ ВЫБОРА #1 — детерминизм процесса vs изоляция экспертизы (агент vs воркфлоу) — ГЛАВНОЕ

> Добавлено 2026-06-09 (Антон). Это первый вопрос ПЕРЕД матрицей надёжности ниже. Антон: «как правильно решать — агент или воркфлоу?».

**Решай по вопросу «ЧТО ГЛАВНЫЙ РИСК?»:**

| Главный риск | Метод | Почему |
|---|---|---|
| **Пропустят шаг / не применят правило / собьётся порядок / нужна повторяемость 1-в-1** | **ВОРКФЛОУ** | Воркфлоу = КОД → гарантирует: (а) точно те действия, (б) в той последовательности, (в) обязательные оценки/гейты ВСЕГДА запустятся в нужном месте, (г) оркестрация НЕ дрейфует (код не забывает шаг). Это его суть. |
| **Тяжёлая работа сожжёт контекст / нужна изолированная экспертная роль / one-off делегация** | **АГЕНТ** | Изоляция контекста + переиспользуемая роль. НО НЕ гарантирует полноту/порядок — внутри агент = LLM, может «забыть» шаг. |
| **subagent-API падает (403) / нельзя пред-прописать / адаптивность** | **MAIN / Conductor-LITE** | Надёжность + гибкость, но LLM дрейфует → нужна дисциплина/чеклист. |

**КОРЕНЬ (почему детерминизм важен):** LLM (агент ИЛИ main-процесс) **дрейфует** — забывает применить правило, пропускает шаг, сглаживает (особенно в Dumb Zone >40% контекста). **Воркфлоу убирает дрейф ПРОЦЕССА** — последовательность и обязательные проверки зашиты в код, их физически нельзя «забыть». Это подтверждено: правила про /clear, оба аккаунта и т.п. main-процесс «вспоминает» с трудом.

**Нюанс (честно):** воркфлоу гарантирует детерминизм СКЕЛЕТА (шаги/порядок/какие гейты запускаются). Внутри каждого шага всё ещё LLM-агент → КОНТЕНТ может варьироваться. Лечится: зашить в код **рубрику/схему/порог (gate)** для каждой оценки → тогда и «оценки что нужны» (пункт в) детерминированы.

**Не «или-или»:** воркфлоу ДИРИЖИРУЕТ агентами. Идеал повторяемого клиентского процесса (КП, SEO-аудит, deploy) = **воркфлоу** (детерминированный порядок + обязательные гейты: factcheck/рубрика/верификация) → каждый шаг = вызов нужного агента/скилла.

**Применение к нам:**
- Повторяемые процессы где «пропустить = провал» (КП-пайплайн, SEO-аудит со всеми проверками, deploy-чеклист, фактчек-гейты) → **ВОРКФЛОУ** (ради а/б/в/г).
- Разовая тяжёлая делегация («сделай аудит этого клиента») → **АГЕНТ** (`seo-specialist` и т.п.).
- 403/адаптив → **main/Conductor-LITE**.

## ОСЬ ВЫБОРА #2 — матрица надёжности (что когда)

| Метод | Когда применять | Надёжность | Зависит от субагентов? |
|---|---|---|---|
| **Main-процесс (последовательно)** | дефолт; детерминированные API/файловые операции; когда субагенты падают | ✅ высшая | нет |
| **Conductor-метод LITE** (spec→план-чеклист→поэтапное выполнение с верификацией каждого шага, в main) | структурный multi-step (контент/лендинг/документ/миграция), где нужно качество+контроль БЕЗ параллели | ✅ высокая (main, без 403-риска) | нет |
| **Conductor FULL** (`/conductor:setup`+`:new`+`:implement`) | **только software-проекты** (код, tech-stack, TDD, % покрытия). Создаёт `conductor/` scaffolding | ✅ | нет (main) |
| **Workflow (tool)** | genuine параллельный fan-out независимых задач (ревью N файлов, рой-аудит) | ⚠️ зависит от здоровья subagent-API | **ДА** — при 403/throttle даёт 0 |
| **Agent рой (background)** | 2-4 независимых задачи параллельно | ⚠️ то же + socket-нестабильность | **ДА** |
| **VPS combine (2-й аккаунт)** | удвоить лимит на независимых не-CONFIRM задачах | ⚙️ | частично |

## Правила
1. **Субагенты (Workflow/рой) падают 403/socket → немедленно переключиться на Conductor-LITE или main-процесс.** Не долбить падающий рой (антипаттерн повтора).
2. **Conductor FULL — НЕ для маркетинг-артефактов** (КП/лендинг/контент). Его setup спрашивает tech-stack/TDD/styleguides — off-domain. Для них = Conductor-LITE (метод без scaffolding).
3. **Conductor-LITE (рекомендуемый дефолт для структурного не-кода):** (а) написать spec (что делаем, блоки, источники, что блокировано); (б) план-чеклист по блокам; (в) выполнять блок-за-блоком, **верификация каждого** (factcheck/visual/curl) → коммит; (г) не отклоняться от плана без approve.
4. **Workflow — когда subagent-API здоров** И задача реально параллельна (N независимых элементов). Текстовый возврат надёжнее schema (schema-reluctance ломала 3/8 в сессии).
5. **«Без потери качества»** = верификация на каждом шаге (Conductor-LITE) ИЛИ adversarial-проверка результата роя. Не «нагенерил и забыл».

## Антипаттерны
- ❌ Гнать Workflow/рой когда субагенты 403 (0 результата, трата времени).
- ❌ Полный Conductor-setup на лендинг/КП (off-domain церемония).
- ❌ Параллель ради скорости без верификации каждого результата (= «много ошибок», чего боится Антон).
- ❌ Повторять падающую оркестрацию >1 раза вместо смены метода.

## Прецедент
- 2026-06-04 USmile: 1-й Workflow-рой (QA лендингов) дал 5/8 (3 schema-fail); 2-й рой (UX-ревью) — 3/3 **403** (0 токенов). Переключились на main-процесс (детерминированные фиксы лендингов/PPC — 0 ошибок). Conductor-FULL отвергнут как off-domain для content-swap; принят Conductor-LITE метод.

## ОСЬ ВЫБОРА #3 — антиколлизия параллельных субагентов (round_table-validated, 2026-06-20)
> **Прецедент 2026-06-20 USmile:** 2 субагента (`yarmolinsky-fix` + `allon4-build`) писали в ОДНИ файлы → коллизия (байт-идентичные файлы, перезапись); текстовый «стоп» проигнорён (агенты доделали и закоммитили); оркестратор не знал что сделано → реконструировал из git reflog вручную → по ошибке удалил реальную работу (восстановил из git). Корень — отсутствие изоляции записи + надёжной остановки.
> **Источник заимствований:** Anthropic multi-agent engineering post (anthropic.com/engineering/multi-agent-research-system). **Валидация:** `round_table` (llama-3.3-70b + gpt-oss-120b + qwen3-32b, синтез llama; deepseek-r1 был недоступен; уверенность MEDIUM), 2026-06-20. AUTHOR: round_table(3 модели) · synthesis llama · 2026-06-20.

При ПАРАЛЛЕЛЬНОМ рое субагентов (2+) применять, по приоритету:

| # | Правило | Приоритет |
|---|---------|-----------|
| 1 | **ИЗОЛЯЦИЯ записи.** Каждый параллельный субагент пишет ТОЛЬКО в свой изолированный артефакт: отдельный файл (`<name>-<agentid>.html`) ИЛИ git worktree/ветка (`isolation:'worktree'` в Workflow; `git worktree add`) → отдаёт оркестратору ССЫЛКУ. **НИКОГДА 2+ агента в один файл** (это race / «испорченный телефон»). Дизайн-варианты — раздельные файлы, мердж/выбор ПОСЛЕ валидации. | ★★★ критично (лечит коллизию) |
| 2 | **CANCELLATION что реально работает.** Текстовый «стоп» субагент игнорирует. Нужен: cancellation-маркер (файл/токен), субагент периодически проверяет; оркестратор ставит «cancel»; watchdog с TTL принудительно завершает зависший. Для Agent-роя: `shutdown_request`; если игнорит — НЕ плодить новые, дождаться idle / закрыть фон-сессию. | ★★★ (лечит «стоп проигнорён») |
| 3 | **ТРЕЙС/МАНИФЕСТ коммитов.** Оркестратор ведёт явный лог «агент X → создал/закоммитил Y (hash)». НЕ узнавать что агент сделал из reflog post-factum. | ★★ |
| 4 | **ЧЕКПОЙНТ после стадии.** Сохранять состояние → resume со стадии N (не с нуля). Вторично — не лечит коллизию, внедрять после 1-3. | ★ условно |

**Антипаттерны (ровно прецедент 20.06):** 2 агента пишут в один файл; текстовый «стоп» как надёжная остановка; узнавать результат агента из reflog вручную; удалять артефакт агента не проверив его коммиты в git; worktree на каждого без `git worktree prune` (залипают).

**Enforcement (TBD, `enforcement-primitives` — правило без хука = текст):** кандидаты — `pre-agent-overlap-guard.sh` (2 агента с пересекающимся target-файлом → warn), cancellation-маркер-механизм, manifest auto-log. Не регистрировать без approve Антона + тест (хук на 3 аккаунта).
