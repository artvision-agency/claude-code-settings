## Часть 1 — ДЕТЕРМИНИЗМ ПО УМОЛЧАНИЮ

Любой **повторяемый** процесс (где «пропустить шаг = провал», где важен порядок, где нужна воспроизводимость 1-в-1) — оформляется как **код** (workflow `.js` / скрипт / хук), НЕ «на память LLM».

**Почему:** LLM (агент ИЛИ main-процесс) дрейфует — забывает шаг, меняет порядок, сглаживает (особенно в Dumb Zone >40%). Воркфлоу/скрипт = код → последовательность и обязательные гейты физически нельзя «забыть».

| Риск | Решение |
|---|---|
| Пропустят шаг / собьётся порядок / нужна повторяемость | **Воркфлоу/скрипт** (детерминированный скелет) |
| Тяжёлая разовая делегация, изоляция контекста | Агент (НЕ гарантирует полноту — внутри LLM) |
| subagent-API падает (403) / адаптивность | main / Conductor-LITE по чеклисту |

Где контент внутри шага может варьироваться — зашивать **рубрику/схему/порог (gate)** в код, тогда детерминирован не только скелет, но и критерий оценки.

## Часть 2 — ЖЁСТКАЯ ПРОВЕРКА ПОСЛЕ СОЗДАНИЯ (обязательный гейт, не «потом»)

После создания/правки ЛЮБОЙ детерминизации (workflow / скрипт / хук / LaunchAgent) — СРАЗУ прогнать verification-gate. Без него артефакт НЕ считается готовым.

### 2.1. Синтаксис парсится
- JS workflow: `node --check <file>`
- bash хук: `bash -n <file>`
- python: `python3 -m py_compile <file>`
- JSON/YAML: `jq . <file>` / `python3 -c "import yaml,sys;yaml.safe_load(open(...))"`
- Не парсится → СТОП, чинить. (Прецедент: skill-required хук в этой сессии — bash-баг блокировал всё.)

### 2.2. Логика не сломана
- Все обязательные шаги/гейты на месте (backup, verify, factcheck, CONFIRM-барьер).
- Нет «висячих» ссылок: workflow ссылается на существующие скрипты/скиллы/правила (grep проверить).
- Выход каждой фазы — вход следующей (нет разрыва данных).

### 2.3. Последовательность vs параллельность — ПРАВИЛЬНАЯ (ключевое по Антону)
Проверить ЯВНО, что выбран нужный режим, и он действительно реализован в коде:

| Должно быть | Признак в коде | Когда |
|---|---|---|
| **ПОСЛЕДОВАТЕЛЬНО** | `for(...){ await agent() }` / pipeline по одному / await цепочкой | зависимые шаги (B нужен output A); **write в один общий ресурс** (кабинет/файл/БД — нельзя параллелить!); CONFIRM-операции |
| **ПАРАЛЛЕЛЬНО** | `await parallel([...])` / `pipeline(items, ...)` | независимые элементы (N файлов, N кампаний, N линз ревью); fan-out |

- **Барьер уместен?** `parallel()` = ждёт все. Нужен только если следующая фаза требует ВСЕ результаты (dedup/синтез/early-exit). Иначе → `pipeline()` (без барьера).
- **Анти-проверка:** не параллелятся ли write в общий ресурс (race → порча данных)? Не гонятся ли последовательно независимые задачи (теряем время)?
- Прогнать мысленно граф: что от чего зависит → совпадает ли с кодом.

### 2.4. Verification на исполнении (runtime gate)
Сам артефакт должен СОДЕРЖАТЬ проверку результата: backup→действие→**verify повторным чтением числами** (Errors:[] недостаточно). «Нагенерил и забыл» = запрещено (cherny #2, bulletproof verification loop).

## Чеклист (после создания детерминизации)
- [ ] Синтаксис парсится (node/bash -n/py_compile)
- [ ] Все гейты/обязательные шаги на месте
- [ ] Ссылки на скрипты/скиллы/правила существуют (grep)
- [ ] Последовательное — последовательно (зависимости, write в общий ресурс)
- [ ] Параллельное — параллельно (независимые), барьер только если нужен синтез
- [ ] Встроена runtime-verify (verify результата числами, не «на слово»)
- [ ] (для хука/LaunchAgent) зарегистрирован + тест 3 кейса блок + 3 пропуск + bypass

## Антипаттерны
- ❌ Повторяемый процесс «на память» вместо workflow/скрипта (дрейф LLM).
- ❌ Создать workflow/скрипт и не прогнать `node --check`/`bash -n` (битый код тихо лежит — прецедент orphan-хуков self-corrections #18).
- ❌ Параллелить write в один кабинет/файл/БД (race condition).
- ❌ Гнать последовательно независимые задачи (потеря времени).
- ❌ `parallel()` (барьер) там, где хватает `pipeline()` (лишнее ожидание).
- ❌ Артефакт без встроенной runtime-verify результата.
- ❌ «Проверю потом» — verification-gate СРАЗУ после создания, иначе не готово.
