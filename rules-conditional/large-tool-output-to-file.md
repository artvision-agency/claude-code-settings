# Большой ответ инструмента/API → в ФАЙЛ, в контекст только СВОДКА (token-diet, общее)

> **Установлено:** 2026-06-21 (Антон). Обобщение PPC-находки на ВСЕ обращения к данным/API.
> **Доказательство (замер логов за неделю):** гигантские tool-ответы (>50KB) дают ВСЕ инструменты — lighthouse 1808, yandex 1782, SEMrush 1743, Wordstat 1671, Topvisor 1285, crawl 736, Metrika 289, Webmaster 226. Топ — **5.3 МБ в одном ответе (~1.3М токенов)**. Они оседают в контексте и переотправляются каждый turn = главный пожиратель токенов.
> **Связано:** `ppc-excel-first-then-api`, `cost-aware-alternatives-first`, `numbers-deterministic-meaning-llm`, `determinism-first-and-verify`, `proven-tools-first`, `TOKEN-DIET-FINDINGS.md`.

## Правило (HARD) — касается ВСЕХ API/инструментов с большими ответами
Любой инструмент/API, возвращающий **дамп данных** (Я.Директ, Wordstat, Метрика, Вебмастер, Topvisor, SEMrush, keys.so, Screaming Frog crawl, Lighthouse, reviews-API, любой list/report endpoint):
1. **Ответ → в ФАЙЛ** (`clients/<slug>/<tool>/data/*.json|csv`), в чат/контекст — **только СВОДКА** (N строк/статусы/ключевые числа). НЕ печатать полный дамп в tool-результат.
2. **Читать файл ТОЧЕЧНО** (grep/jq/head/awk по нужному полю), НЕ `Read` целиком (core.md: >2K строк → Grep, >10K → только Grep).
3. **Минимизировать ответ на источнике:** FieldNames/fields/columns только нужные; пагинация/лимит; фильтр на стороне API.
4. **jq/python-обработка** больших JSON/CSV вместо «прочитай весь файл».
5. **Числа из дампа** — детерминированно (jq/awk), не «глазами LLM» (`numbers-deterministic-meaning-llm`).

## Антипаттерны (то, что жгло — 5.3МБ в одном ответе)
- ❌ Печатать полный ответ API/инструмента в чат (Lighthouse JSON, SEMrush-дамп, Wordstat-список, crawl-CSV целиком).
- ❌ `Read` большого CSV/JSON целиком в контекст (Screaming Frog sf-out, lighthouse lhr.json).
- ❌ Запрашивать все поля/строки вместо нужного среза.
- ❌ Держать дамп в контексте «на всякий» — он переотправляется каждый turn.

## Как правильно (паттерн)
- Скрипт делает запрос → пишет результат в файл → ВОЗВРАЩАЕТ сводку (1-5 строк).
- Claude видит сводку; нужна деталь → `jq '.path' file` / `grep pattern file` / `awk` — точечно.
- Пример: `seo-toolkit.py` пишет в `seo/<date>/`, Claude читает нужный CSV через grep, не целиком.

## 🔴 ДЕТАЛИЗАЦИЯ СОХРАНЯЕТСЯ ПОЛНОСТЬЮ (HARD — Антон 2026-06-21)
Консолидация/сводка ≠ потеря данных. Принцип: данные НЕ сокращаются, а ПЕРЕМЕЩАЮТСЯ (контекст → файл).
- **В ФАЙЛ — 100% детализация** по КАЖДОМУ каналу/кампании/источнику/строке. Ничего не выбрасывается, не агрегируется с потерей. Полный сырой ответ сохраняется.
- **В КОНТЕКСТ — навигационная сводка + ИНДЕКС** (что где лежит, сколько по каждому каналу, путь к файлу), НЕ урезанные данные.
- **Деталь любого канала достаётся из файла ПОЛНОСТЬЮ** по запросу (jq/grep/awk по нужному срезу) — в любой момент, без потерь.
- Разделять хранение ПО КАНАЛАМ: отдельный файл/секция на канал (Поиск/РСЯ/Ретаргет/каждая кампания/каждый источник) — чтобы достать детализацию конкретного канала точечно, не тревожа остальные.
- **ЗАПРЕТ:** «ужать в общую сводку» теряя детали каналов; агрегировать так, что нельзя восстановить по-канально; выбрасывать поля «ради краткости». Краткость — только в КОНТЕКСТЕ, в ФАЙЛЕ — всё.

## Триггеры (когда правило срабатывает)
- **Авто (paths):** работа в seo/ppc/ads/data/analytics-папках или с файлами *metrika/wordstat/topvisor/semrush/lighthouse/crawl/direct/webmaster* → правило грузится.
- **По действию:** любой вызов API/инструмента, который МОЖЕТ вернуть >50KB (list/report/export endpoint, crawl, audit) → ПЕРЕД вызовом решить: писать в файл + по-канально, сводку в контекст.
- **По объёму:** если ответ уже пришёл >100KB в контекст — следующим шагом сбросить в файл, дальше работать с файлом.

## Кандидат-хук (свежая сессия, с тестами — self-corrections #18)
