## 🔴 ENFORCEMENT — DEFAULT для ВСЕХ сессий и ВСЕХ проектов (Антон 2026-06-15, HARD)

> **Прецедент:** OPS Task Runner (security-sensitive автономный `claude -p`) собран 14.06 БЕЗ Codex-ревью — правило было opt-in по ключевому слову, его просто не позвали. Антон: «эта схема должна применяться ОБЯЗАТЕЛЬНО во всех сессиях где есть программирование (включая соседнюю по автоборгу)». По мета-правилу self-corrections #18: *правило без enforcement → пропускается → нужен хук.*

**Codex-dev-lifecycle — НЕ opt-in по триггеру, а ДЕФОЛТ для любой нетривиальной разработки кода, в ЛЮБОЙ сессии, на ЛЮБОМ проекте (Артвижн, клиенты, инфра, автоборг и т.д.).**

- **Что под обязательность:** скрипты (`.py/.sh/.js`) от ~50 строк или меняющие прод-поведение, named workflows (`.claude/workflows/*.js` — это код!), хуки, API-интеграции, демоны/LaunchAgent/systemd, security-чувствительное (auth/деньги/прод/автономное исполнение/токены). Для них — план (Claude) → **Codex-ревью плана** → build → **Codex-ревью кода** → рефактор, луп до «ожидание==результат» (`Workflow({name:'codex-dev-lifecycle'})`).
- **Что НЕ под обязательность (bypass):** опечатка/однострочник, конфиг-правка, маркетинг-работа (PPC/контент/КП — НЕ код), тривиальный glue <~50 строк без прод-эффекта.
- **Деградация при 403 Codex** (известная нестабильность): план/код-ревью через `codex CLI` напрямую (`codex:codex-cli-runtime`) ИЛИ round_table (open-source консилиум) ИЛИ задокументированное adversarial main-ревью. НЕ «пропустить ревью», НЕ «блок навсегда» — заменить ревьюера, не отменить ревью.
- **Кросс-сессионность:** это правило грузится КАЖДУЮ сессию (sync на 3 аккаунта). Хук-enforcer (`pre-tool-codex-lifecycle-guard.sh`, харнес-уровень) срабатывает в ЛЮБОЙ сессии при Write/Edit кода без признака Codex-ревью в transcript → warn. Уже-запущенная сессия (напр. автоборг) подхватит хук file-watcher'ом (cherny #9), правило — после `/clear` или git-pull. Для немедленного применения в running-сессии — она запускает свою разработку через `Workflow({name:'codex-dev-lifecycle'})`.

## 🤝 PLAN = ПЕРЕГОВОРЫ Codex↔Claude, не диктат (Антон 2026-06-15, «do it»)

> Антон: «было бы прикольно, если бы Codex вместе с Claude вели переговоры на старте по планированию — не один Codex планирует и забирает, а они ведут переговоры и принимают решение. У Claude есть факты, которых нет в Codex.»

Фаза PLAN — **двусторонний диалог**, а не «Codex вынес вердикт → Claude молча правит»:
1. **Claude драфтит план** (у него наш контекст: правила/память/CONFIRM/состояние проекта/бизнес-факты — то, чего у Codex НЕТ).
2. **Codex adversarial-критикует** (другое семейство, ловит слепые пятна).
3. **Claude ОТВЕЧАЕТ на каждое замечание** по findings-evaluation-matrix (Дементьев): **Applied** (принял, правлю) / **Re-scoped** (переформулировал) / **Rejected + ПОЧЕМУ** (отклонил с фактом/правилом, которого Codex не знает — напр. «это CONFIRM-операция по security.md», «passthrough≠MRR», «white-label AdvertMed», «ФЗ-323»). Отклонение — эмпирически обоснованное, не голословное.
4. **Codex реагирует на ответы Claude** (оспаривает отклонения ИЛИ соглашается) → следующий раунд.
5. **Сходимся на СОГЛАСОВАННОМ плане** (оба «за»), не на «Codex сказал». Луп до consensus ИЛИ maxPlanRounds (тогда фиксируем разногласие явно для человека).
- Реализация: расширить `codex-dev-lifecycle.js` фазу PLAN — добавить раунд «Claude-response на findings» (Applied/Re-scoped/Rejected+why) → Codex-реакция → consensus-чек, а не односторонний PLAN_VERDICT. Это правка workflow-кода → САМА идёт через этот же lifecycle (ест свой dogfood).
- **Доменные факты Claude бьют Codex** (findings-фильтр, `codex-dev-lifecycle.md` существующая секция): Codex не знает наших CONFIRM-барьеров/white-label/ТАБУ-AI/passthrough — Claude вправе Rejected с обоснованием, Codex не «начальник».

## Метод Хахалева — конкретика (закрепить точно)
1. **Две модели — потому что одна модель пропускает свои ошибки** (помнит почему так решила, не ставит под сомнение — как вычитка своего текста). Разные архитектуры+pretraining = разные слепые пятна. Одна пишет, другая ревьюит **adversarial** (с позиции противника).
2. **Ревью ПЛАНА важнее ревью кода** (уникальность подхода). План ревьюится из Plan Mode ДО кода — ошибка в плане (неправильная декомпозиция, пропущенная зависимость) дороже бага в коде (код может быть корректным, но решать не ту задачу / не в том порядке).
3. **Нюанс (Хахалев): человек/Claude планирует ЛУЧШЕ Codex** — план требует контекста ВНЕ кодовой базы (бизнес-цели, приоритеты, рынок). Поэтому: **Claude планирует** (у него наш контекст: правила/память/CONFIRM), **Codex РЕВЬЮИТ план** adversarial. Не «Codex планирует вместо Claude» — Codex критикует план Claude.
4. **Вердикт ревью: `APPROVED` / `REVISE`.** При REVISE → Claude читает замечания, правит → цикл. **До 5 раундов, на практике 2-3.**
5. **Codex в read-only** на ревью (не правит сам).
6. **Структура adversarial-промпта Codex'у:**
   - `<attack_surface>` — конкретный чеклист (авторизация, целостность данных, race conditions, rollback safety, …под задачу).
   - `<finding_bar>` — каждое замечание обязано ответить: ЧТО сломается · ПОЧЕМУ уязвимо · ИМПАКТ · РЕКОМЕНДАЦИЯ.
   - `<scope_exclusions>` — НЕ комментировать стиль, игнорировать спекулятивные улучшения.
   - **Правило: одно веское замечание > пяти слабых.** Ложные срабатывания подрывают доверие (= наш `quality.md` challenge, finding-bar).
> **Связано:** `consilium-matrix.md` (codex-rescue = backend/архитектура/2-е мнение), `orchestration-method-selection.md` (агент vs воркфлоу), codex-скиллы (`codex:gpt-5-4-prompting`, `codex:codex-cli-runtime`, `codex:codex-result-handling`), `bulletproof-patterns.md` (challenge loop), `superpowers:writing-plans`.

## Когда применять — ГРАНИЦА: КОД vs МАРКЕТИНГ-РАБОТА (ответ Антону 11.06)

**Codex-lifecycle = ревью КОДА и ПЛАНОВ разработки. НЕ ревью маркетинговой работы.** Разные домены, разные смыслы:

| Объект | Codex применять? | Чем ревьюим |
|---|---|---|
| **КОД:** скрипты Python/bash, named workflows `.claude/workflows/*.js` (они = код!), хуки, gantt_api.py, ops-дашборд, боты, API-интеграции | ✅ ДА — план→Codex-ревью→build→Codex-ревью→луп | Codex (adversarial) |
| Security-критичный код (auth/деньги/API) | ✅ ДА обязательно | Codex |
| Архитектурное решение, рефакторинг >~50 строк | ✅ ДА | Codex |
| **PPC-РАБОТА:** настройка кампаний, семантика, креативы, ставки, минус-слова, посадочные-копирайт | ❌ НЕТ — это не код | наши PPC-правила + `/factcheck` + round_table + консилиум спецов |
| Клиентский контент: КП, статьи, лендинг-копирайт, посты | ❌ НЕТ | наши quality-gates (factcheck, _compliance-checklist, round_table) |
| Тривиалка: опечатка, цена, одностроч-фикс | ❌ НЕТ (overkill) | — |

**Ключ:** Codex проверяет **исходный код продукта**, а не **маркетинговый результат**. Если PPC-«продукт» = это **JS-workflow** (`ppc-campaigns.js`, `ppc-rk-creation.js`) → Codex ревьюит ЛОГИКУ workflow-кода (баги в оркестрации). Но САМИ кампании/креативы (output) → наши домен-гейты (round_table, factcheck, PPC-правила), НЕ Codex. Codex не разбирается в Я.Директе — он разбирается в коде.

**Для PPC-сессии Антона:** применять Codex к workflow-КОДУ (если правишь `.js`-воркфлоу или скрипты PPC) — да. К самой настройке рекламы — нет, там наш стек (`ppc-metrika-counters`, round_table, консилиум).

## Цикл (4 фазы)

### 1. PLAN — Claude планирует, Codex РЕВЬЮИТ план (до кода)
- **Claude** составляет план (у него наш контекст: правила/память/CONFIRM/бизнес-цели — поэтому планирует он, не Codex; нюанс Хахалева).
- План → **Codex на adversarial-ревью** (`Agent subagent_type codex:codex-rescue`, read-only) со структурой `<attack_surface>`/`<finding_bar>`/`<scope_exclusions>` → вердикт `APPROVED`/`REVISE`.
- REVISE → Claude правит план → повтор (до 5, обычно 2-3). APPROVED → к коду.
- Развилка агент-vs-воркфлоу (`orchestration-method-selection` ось #1): повторяемый процесс → воркфлоу; разовая разработка → план + main-исполнение.

### 2. BUILD — Claude исполняет по плану
- Main-процесс (надёжнее субагентов при 403) ИЛИ воркфлоу с гейтами. Claude пишет код по плану Codex, применяя наши правила (тесты, фактчек, бэкап перед прод-правкой).

### 3. STAGED REVIEW — Codex ревьюит ПОЭТАПНО (не только в конце)
- После каждого значимого этапа/milestone (не всё разом) → Codex code-review (`codex:codex-rescue`): баги, security, severity. Поэтапно = ловим раньше, дешевле фикс.
- Claude применяет фиксы CRITICAL/HIGH сразу; MID/LOW — по решению.
- Для security-кода — обязательно (прецедент 11.06: Codex поймал что HMAC-секрет не задан, CSRF, PIN в JS).

### 4. REFACTOR — если ревью флагает, рефактор + Codex перепроверяет
- Рефакторинг по находкам → Codex re-review что фикс корректен и не внёс регресс.
- Цикл REVIEW↔REFACTOR пока не PASS (или осознанный остаток в TODO).

### 5. LOOP до «ОЖИДАНИЯ = РЕЗУЛЬТАТ» (Антон 11.06 — главное условие выхода)
- **Истинное условие завершения лупа — НЕ «Codex одобрил код», а «исходные ожидания сходятся с конечным результатом».** Итерации план→build→ревью→рефактор крутятся, пока **ожидание == факт** (цель достигнута), не просто пока код «чистый».
- В конце КАЖДОГО лупа — сверка результата с ИСХОДНОЙ задачей/планом (наш `/goal` Фаза 5 + `superpowers:verification-before-completion`): что просили vs что вышло. Расхождение → ещё итерация.
- Код может быть Codex-APPROVED, но решать не ту задачу → луп НЕ закрыт, пока результат ≠ ожидание.
