# Project Audit — Полный аудит проекта

Два уровня аудита в одном скилле:
- **Часть A**: Инфраструктура Claude Code (.claude/ настройка)
- **Часть B**: Качество кода (Claude Certified Architect checklist)

## When to Use

- Новый проект без `.claude/` инфраструктуры
- Существующий проект — навести порядок
- Пользователь говорит "аудит", "настрой .claude", "создай хуки", "проверь качество"
- После завершения крупной фичи — проверить что ничего не упущено

# ЧАСТЬ A: Инфраструктура Claude Code

Выполняй **строго по порядку**. Каждый шаг — отдельная задача в TaskCreate.

### Step 1: Анализ текущего состояния

Проверить наличие и содержимое:

```
.claude/
  skills/         — есть ли обязательные (tdd, solid-dry-kiss, ddd-hexagonal)?
  rules/          — есть? покрывают ли стиль, профиль, архитектуру?
  templates/      — есть? шаблоны под стек проекта?
  scripts/        — есть? hooks подключены в settings?
  agents/         — есть? субагентные инструкции?
CLAUDE.md         — сколько строк? (>200 = раздут) Есть ли секция Architecture & Methodology?
memory/           — сколько файлов? есть ли устаревшие? есть ли feedback-review-workflow?
settings.local.json — hooks подключены?
scripts/sync-skills.sh — синхронизация skills настроена?
```

Вывести таблицу: что есть ✅, чего нет ❌, что требует улучшения ⚠️.

### Step 2: Обязательные Skills

Три skill'а ОБЯЗАТЕЛЬНЫ в каждом проекте (`.claude/skills/`):

| Skill | Назначение |
|-------|-----------|
| **tdd** | RED-GREEN-REFACTOR, тесты перед кодом |
| **solid-dry-kiss** | SOLID, DRY, KISS, YAGNI принципы |
| **ddd-hexagonal** | Domain-Driven Design + Hexagonal Architecture |

Для каждого отсутствующего:
1. Проверить в `~/claude-code-settings/skills/` (источник)
2. Если есть — скопировать в `.claude/skills/`
3. Если нет — создать минимальный skill

**По стеку проекта** — подключить дополнительные:
- Python → `python-testing-patterns`
- aiogram → `aiogram-patterns`
- React/TS → `react-best-practices`
- SQLAlchemy async → `sqlalchemy-async`

### Step 3: Синхронизация Skills

Шаблон скрипта: `~/claude-code-settings/scripts/sync-skills-template.sh`

Настройка:
1. Скопировать шаблон в `scripts/sync-skills.sh` проекта
2. Изменить `PROJECT_DIR`, `SOURCE_REPO`, `SKILLS` под проект
3. `chmod +x scripts/sync-skills.sh`
4. Добавить в cron: `crontab -e`

Логика скрипта:
- `git pull` source repo (claude-code-settings)
- Хеш по содержимому файлов (не по путям) — `find | sort | xargs cat | md5sum`
- Source изменился → `rsync -a --delete source/ target/` (обновить проект)
- Проект изменился → `rsync -a --delete target/ source/` + git push
- Оба изменились → **CONFLICT** → уведомление в Telegram (BOT_TOKEN + CHAT_ID из .env)
- Хеши хранятся в `data/.skills-hashes/`

Cron (ежедневно в 6:00 UTC):
```
0 6 * * * /path/to/scripts/sync-skills.sh >> data/logs/sync-skills.log 2>&1
```

**Важно:** НЕ использовать `cp -r` для синхронизации — создаёт вложенные копии. Только `rsync -a --delete` с trailing slash.

### Step 4: Hooks (максимальный эффект)

Создать `.claude/scripts/` с тремя хуками:

**hook-post-commit.sh** — напоминание после `git commit`:
- Обновить memory/docs
- Нужен ли deploy
- Нужен ли git push

**hook-pre-deploy.sh** — блокировка деплоя:
- Проверка непушнутых коммитов (exit 2 если есть)
- Warning о незакоммиченных изменениях
- Адаптировать команду деплоя под проект

**hook-stop-reminder.sh** — чеклист завершения сессии:
- Memory обновлена?
- Тесты проходят?
- Коммит/push сделан?
- Deploy нужен?

Подключить в `settings.local.json`:
```json
{
  "hooks": {
    "PreToolUse": [{"matcher": "Bash", "hooks": [{"type": "command", "command": "bash .claude/scripts/hook-pre-deploy.sh"}]}],
    "PostToolUse": [{"matcher": "Bash", "hooks": [{"type": "command", "command": "bash .claude/scripts/hook-post-commit.sh"}]}],
    "Stop": [{"hooks": [{"type": "command", "command": "bash .claude/scripts/hook-stop-reminder.sh"}]}]
  }
}
```

### Step 5: Rules

Создать `.claude/rules/` — вынести из CLAUDE.md пассивный контекст:

**coding-style.md** (globs: `["**/*.{py,ts,js,go}"]`):
- Логирование (формат, библиотека)
- DB-паттерны (ORM, сессии, миграции)
- Специфичные gotchas проекта

**profile.md** (globs: `["**/*"]`):
- Язык общения
- Уровень автономности
- Что НЕ делать без спроса

**architecture.md** (globs: `["**/*.{py,ts,js,go}"]`):
- Ключевые архитектурные паттерны
- Ссылки на templates

### Step 6: CLAUDE.md — Architecture & Methodology

Проверить что CLAUDE.md содержит секцию:

```markdown
## Architecture & Methodology
- **TDD**: сначала тесты (RED), потом код (GREEN), потом рефакторинг
- **SOLID/DRY/KISS**: `.claude/skills/solid-dry-kiss/SKILL.md`
- **DDD + Hexagonal**: `.claude/skills/ddd-hexagonal/SKILL.md`
- Бизнес-логика → `domain/` или `application/` (use cases)
- `webapp/server.py`, `bot/handlers/` — только тонкие адаптеры
- При запуске субагентов ВСЕГДА передавать эти требования в промпт
```

Если нет — добавить. Если CLAUDE.md > 100 строк — вынести детали в rules.

Целевой размер: **60-90 строк**.

### Step 7: Review Workflow (memory)

Проверить что в memory есть `feedback-review-workflow.md`:

```
После выполнения каждой задачи:
1. /aif-verify — проверить что код работает
2. /aif-review — code review
3. /aif-fix — исправить criticals + importants
4. /aif-review — повторный ревью
5. Показать пользователю результат: criticals, importants, suggestions, вопросы
6. Ждать решения пользователя
```

Также проверить `feedback-agents-ddd-tdd.md`:
```
При запуске субагентов ВСЕГДА передавать:
1. TDD: прочитай .claude/skills/tdd/SKILL.md
2. SOLID/DRY/KISS: прочитай .claude/skills/solid-dry-kiss/SKILL.md
3. DDD + Hexagonal: прочитай .claude/skills/ddd-hexagonal/SKILL.md
```

### Step 8: Templates

Создать `.claude/templates/` — шаблоны по стеку проекта:
- **Python web**: новый эндпоинт, миграция, модель, тест
- **React/TS**: новый компонент, страница, хук
- **Bot (aiogram)**: новый хендлер, FSM, клавиатура
- **Scraper**: новый парсер сайта
- **General**: новый канал/ресурс

Каждый шаблон: скелет файла + чеклист + где зарегистрировать.

### Step 9: Architecture Decisions

Создать `memory/architecture-decisions.md` если нет.

Формат ADR:
```markdown
## ADR-NNN: Название
**Решение**: что выбрали
**Причина**: почему
**Отвергнуто**: что рассматривали и почему отказались
**Дата**: YYYY-MM-DD
```

### Step 10: Архивирование memory

- Проверить каждый memory-файл на актуальность
- Устаревшие → `memory/archive/`
- Обновить MEMORY.md — убрать мёртвые ссылки
- Целевой размер MEMORY.md: **< 100 строк**

# ЧАСТЬ B: Качество кода (Claude Certified Architect)

На основе Claude Certified Architect — Foundations (5 доменов).
По каждому пункту: ✅ / ❌ / ⚠️ / ➖ (не применимо).

## Домен 1: Агентная архитектура и оркестрация (27%)

### 1.1 Агентный цикл
- [ ] Используется `stop_reason` для определения завершения (не парсинг текста)
- [ ] Полная история передаётся в каждом API-запросе
- [ ] Есть лимит итераций как защита (но не основной механизм остановки)
- [ ] Результаты инструментов добавляются в контекст для следующей итерации

### 1.2 Мультиагентная система
- [ ] Архитектура "звезда": координатор + специализированные субагенты
- [ ] Контекст передаётся субагентам ЯВНО (не наследуется автоматически)
- [ ] Координатор динамически выбирает нужных субагентов
- [ ] Координатор агрегирует результаты и проверяет пробелы

### 1.3 Декомпозиция задач
- [ ] Сложные задачи разбиты на подзадачи (не "всё в одном промпте")
- [ ] Выбран правильный тип: Prompt Chaining (предсказуемые) или адаптивная (открытые)
- [ ] Мультиаспектные задачи разбиты на отдельные проходы (не один проход на всё)
- [ ] Параллельные подзадачи запускаются параллельно

### 1.4 Хуки и гарантии
- [ ] Критичные правила (финансы, безопасность) реализованы через хуки (100% гарантия)
- [ ] Некритичные предпочтения — через промпт-инструкции
- [ ] PreToolUse хуки блокируют опасные вызовы
- [ ] PostToolUse хуки нормализуют форматы данных

### 1.5 Управление сессиями
- [ ] Длительные задачи используют --resume с именованными сессиями
- [ ] При устаревшем контексте — новая сессия со сводкой вместо resume
- [ ] fork_session для сравнения подходов

### 1.6 Обработка ошибок
- [ ] Ошибки категоризированы (transient, validation, business, permission)
- [ ] Субагенты пытаются восстановиться локально (1-2 попытки)
- [ ] При неудаче — структурированная ошибка координатору с частичными результатами
- [ ] Нет молчаливого подавления ошибок

## Домен 2: Проектирование инструментов и MCP (18%)

### 2.1 Описания инструментов
- [ ] Описания развёрнутые: что делает, что возвращает, форматы, граничные случаи
- [ ] Похожие инструменты явно разграничены ("используй X для Y, НЕ для Z")
- [ ] Нет пересекающихся описаний, вызывающих путаницу у модели

### 2.2 Обработка ошибок MCP
- [ ] Используется флаг `isError` для ошибок
- [ ] Ошибки содержат категорию, isRetryable, attempted_query, partial_results
- [ ] Пустой результат отличается от сбоя (results: [] vs isError: true)

### 2.3 Принцип минимальных привилегий
- [ ] Каждый агент имеет только нужные инструменты (не все сразу)
- [ ] Нет лишних инструментов вне специализации агента
- [ ] Опасные инструменты ограничены по ролям

### 2.4 tool_choice
- [ ] `auto` — по умолчанию
- [ ] `any` — когда нужен гарантированный структурированный вывод
- [ ] Принудительный выбор — для обязательного первого шага

### 2.5 MCP-серверы
- [ ] Проектные интеграции в `.mcp.json` (в VCS)
- [ ] Личные/экспериментальные в `~/.claude.json`
- [ ] Токены через переменные окружения (не захардкожены)
- [ ] `.mcp.json` в корне проекта

## Домен 3: Конфигурация Claude Code (20%)

### 3.1 CLAUDE.md
- [ ] Проектный CLAUDE.md — в `.claude/CLAUDE.md` или корне (в VCS)
- [ ] Пользовательский — в `~/.claude/CLAUDE.md` (не в VCS)
- [ ] Директорные CLAUDE.md для специфичных подразделов
- [ ] Используется @path для модульности (нет дублирования)
- [ ] Few-shot примеры кода (правильно + антипримеры)

### 3.2 Path-specific правила
- [ ] `.claude/rules/` с YAML frontmatter и `paths` фильтром
- [ ] Правила загружаются только для релевантных файлов
- [ ] Тестовые конвенции → `paths: ["**/*.test.*"]`
- [ ] API конвенции → `paths: ["src/api/**/*"]`

### 3.3 Навыки и команды
- [ ] Повторяющиеся задачи оформлены как навыки (`.claude/skills/`)
- [ ] Навыки с `context: fork` для изоляции
- [ ] Проектные команды в VCS, личные — в `~/`
- [ ] `allowed-tools` ограничивает доступ навыков

### 3.4 Режим планирования
- [ ] Масштабные изменения (10+ файлов) — через режим планирования
- [ ] Простые правки — прямое выполнение
- [ ] Незнакомая кодовая база — сначала планирование
- [ ] Explore subagent для исследования без загрязнения контекста

### 3.5 CI/CD интеграция
- [ ] Флаг `-p` для неинтерактивного режима
- [ ] `--output-format json` + `--json-schema` для автоматизации
- [ ] Отдельная сессия для ревью (не та, что генерировала код)
- [ ] CLAUDE.md как источник контекста для CI

## Домен 4: Промпт-инженерия и структурированный вывод (20%)

### 4.1 Критерии
- [ ] Явные критерии вместо расплывчатых ("консервативен", "высокоуверенный")
- [ ] Определены границы: что помечать, что НЕ помечать
- [ ] Градация серьёзности (CRITICAL/HIGH/MEDIUM/LOW)

### 4.2 Few-shot примеры
- [ ] 2-4 примера ввода/вывода в промпте
- [ ] Примеры для неоднозначных сценариев
- [ ] Примеры для граничных случаев и формата вывода
- [ ] Примеры для разных форматов данных

### 4.3 JSON-схемы и валидация
- [ ] tool_use для гарантии синтаксически корректного JSON
- [ ] Required только для полей, которые ВСЕГДА есть в источнике
- [ ] Nullable поля для отсутствующей информации
- [ ] Enum с "other" для расширяемости
- [ ] Runtime-валидация (Zod, Pydantic, JSON Schema)

### 4.4 Retry и восстановление
- [ ] Семантическая валидация (бизнес-правила) после структурной
- [ ] Retry с обратной связью при ошибках
- [ ] withRetry для внешних вызовов (exponential backoff + jitter)

### 4.5 Batch API
- [ ] Массовая обработка через Batch API (50% экономия)
- [ ] Срочные задачи — через синхронный API
- [ ] Обработка частичных сбоев (повтор только неудавшихся)

## Домен 5: Управление контекстом и надёжность (15%)

### 5.1 Деградация контекста
- [ ] Ключевая информация в начале и конце (не в середине)
- [ ] Блок "case facts" вне суммаризированной истории
- [ ] Тримминг многословных выводов инструментов (PostToolUse хуки)
- [ ] /compact для длинных сессий (с пониманием рисков потери данных)

### 5.2 Эскалация
- [ ] Явные триггеры эскалации (клиент просит, политика не покрывает)
- [ ] НЕ используется анализ настроений или самооценка уверенности
- [ ] Немедленная эскалация при явном запросе человека

### 5.3 Протоколы передачи (handoff)
- [ ] Структурированная сводка при эскалации (ID, история, рекомендация)
- [ ] Сводка самодостаточна (оператор не видит полный транскрипт)

### 5.4 Происхождение информации
- [ ] Данные содержат источник, URL, дату
- [ ] Конфликтующие данные сохраняются с обоими значениями
- [ ] Даты учитываются при интерпретации (рост vs противоречие)

### 5.5 Валидация качества
- [ ] Метрики по подсегментам (не только агрегатная точность)
- [ ] Стратифицированная выборка для проверки
- [ ] Маршрутизация по уверенности: низкая → человеческое ревью

## Быстрый аудит (топ-15 вопросов)

**Инфраструктура .claude/ (Часть A):**
1. Есть ли обязательные skills (tdd, solid-dry-kiss, ddd-hexagonal)?
2. Есть ли .claude/rules/ с path-specific правилами?
3. Подключены ли hooks в settings.local.json?
4. CLAUDE.md < 100 строк? Есть Architecture & Methodology?
5. Настроена ли синхронизация skills?

**Качество кода (Часть B):**
6. Как определяется завершение агента? (stop_reason vs парсинг текста)
7. Как передаётся контекст между агентами? (явно vs наследование)
8. Как защищены критичные операции? (хуки vs промпты)
9. Насколько подробны описания инструментов?
10. Где хранятся проектные конвенции? (CLAUDE.md в VCS)
11. Есть ли few-shot примеры в промптах?
12. Как валидируется вывод? (структурно + семантически)
13. Есть ли retry для внешних вызовов?
14. Как сохраняется контекст в длинных сессиях?
15. Как обрабатываются ошибки субагентов?

## Common Mistakes

| Ошибка | Исправление |
|--------|-------------|
| Нет обязательных skills | Субагенты не следуют TDD/DDD/SOLID |
| Skills только глобально (~/.claude/) | Субагенты в worktree не видят — копировать в проект |
| Нет синхронизации skills | Обновления из git не попадают в проект |
| Всё в CLAUDE.md | Rules/templates вынести в отдельные файлы |
| Hooks в промптах | Hooks в скриптах — агент не может забыть |
| Нет review workflow | Критические баги попадают в мерж |
| Нет architecture-decisions | Агент предлагает отвергнутые варианты снова |
| Memory растёт бесконечно | Архивировать, держать MEMORY.md < 100 строк |
| Нет валидации входных данных | SQL injection, невалидные данные в БД |
| Нет retry для внешних вызовов | Временный сбой API = потеря заказа |
| Нет few-shot примеров | Claude генерирует код в неправильном стиле |
| Generic Error вместо кастомных | Невозможно отличить 404 от 500 |
| Лечение следствия, а не причины | Найти root cause, а не обходной путь. Пример: sender зависает → не добавлять timeout (следствие), а найти deadlock (причина) |
